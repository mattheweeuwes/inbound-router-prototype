# Inbound router

A work sample for Serif Health's GTM Engineer role, by Matthew Eeuwes. It is a prototype, not a Serif product. The cockpit uses the Sora typeface and Serif's blue, and it carries no Serif logo.

Every inbound lead is resolved to a real healthcare entity on a stable ID, scored, routed and alerted within seconds, and anything uncertain goes to a person. It covers eight inbound doors (demo booking, gated guides, early-access waitlist, sample signup, marketplace listings, API/MCP keys, conference scans, web intent), resolves organizations from free public data (CMS, AHRQ, NPPES), and builds the exact HubSpot and Slack requests. Nothing is sent by default; with a HubSpot service key and `HUBSPOT_LIVE=1` it writes to HubSpot, and it has run that way against a developer test portal.

## Run it

Needs Node 22 (uses `node:sqlite`). Optional: Ollama with `llama3.2:3b` on `127.0.0.1:11434`; without it the rules classifier carries every lead.

```
npm install
npm test               # unit and pipeline tests, no network
npm run replay         # all 40 fixtures through the inbound handler; prints a table and time to alert, writes out/replay.json
                       # (-- --pace 2000 posts like the cockpit's Replay a day, -- --burst posts with no gap)
npm run eval           # rules vs model vs combined against fixtures/gold-labels.json; writes out/eval.md and out/eval.json
npm run eval:gate      # the same evaluation as a gate: exits 1 if v4 on the sealed or held-out set is below its floors, or the local model is unreachable
npm run ci             # what CI runs, in order, stopping at the first failure: typecheck, tests, CI replay, rules-only eval gate, browser test
npm run dev            # http://127.0.0.1:3480 (API under /api, cockpit from public/); sets a local demo signing key and DEMO_ROUTES=1 inline
npm run day            # one working day as a scenario: the 40 fixtures, 15 morning events, a 150-scan list, then outbound, attribution, accounts and the brief; 48 assertions, exits 1 on a failure (docs/day-in-the-life.md)
npm run brief          # the team brief as plain text (what needs a person, enterprise, referrals, lists, expansion, outbound, feature interest, health); writes out/brief.txt and brief.json
npm run list:upload    # a seeded, synthetic 150-scan conference list posted to a running server's event_scan door (-- --count, --list, --base, --seed)
npm run reverse-etl    # company batch upsert from the v_account_scores view and product usage, plus the expansion tasks (dry-run)
npm run rates:fetch    # download Serif's public rate file to data/rates/ (git-ignored); the outbound module loads it at the next start
npm run etl            # rebuild data/registry.sqlite (Python 3.9 standard library only)
npm run gen-fixtures   # regenerate fixtures/submissions.json and gold-labels.json from the table in scripts/gen-fixtures.ts
npm run gen-usage      # regenerate fixtures/usage/events.json and deals.json from the tables in scripts/gen-usage-fixtures.ts
```

Until `data/registry.sqlite` exists with `meta.status = 'complete'`, the app runs on the hand-made `test/fixtures/registry-mini.sql`. It switches to the real registry on its own. `npm run dev` prints which one it is using.

An account already in the CRM that the public registries do not know keeps the CRM record's identity, segment and size.

**Needs a person** (`src/review/`, `api/review.ts`, `docs/DECISIONS.md` #33) is where a person decides what the router would not guess. A tie's candidates each have Use this account; every item has Send to nurture and Not a buyer; a doubt the model raised has It is a buyer; a list's unplaced rows go to nurture in one step. `POST /api/leads/<id>/review` stores the decision with the lead and on its review item (who, a note, when), and the lead runs through the whole pipeline again with it, so a chosen account is scored, routed, alerted and planned for the CRM like any other lead and every later run keeps the choice. The one decision that runs nothing is It is a buyer on a doubt that came after the alert: the lead stays with its rep. The lead's trail shows the decision as its own step, with the route before and now.

The cockpit's **How it works** tab draws all of this in three rows (inbound, outbound, and what is read beside the route) and every box opens a panel that names the tests proving it. `test/how-it-works.test.ts` checks every figure on the tab against the constant it comes from and fails on a figure nothing checks; the registry counts are read from the running registry through `GET /api/how` (#34).

Two things Serif grows on are read beside the classifier, by rules, and never sent to the model. **Enterprise accounts** (`src/enterprise.ts`, `docs/DECISIONS.md` #25): a health system with 8 or more hospitals or hospitals in 3 or more states, a national or Blue payer, or a national broker, consultant or TPA, which is a starting assumption for Serif to replace. Rule R10, after the owner rule and the RevOps rule, sends a person at an enterprise account (or at a known organization whose message carries a deal-size cue such as "bulk license", "all states" or "budget is approved") with tier B or better to a named rep by round-robin, with 5 minutes for tier A and 15 for tier B, instead of a team queue; the first such lead of an account in 30 days also posts a short note to `#enterprise-deals` (dry-run). **Named referrals** (`src/referral.ts`, #26): an answer to "How did you hear about us?" or a phrase such as "the contracting VP at Wrenfield Health recommended you" is resolved to an organization (the CRM's customers first, then the registry, confident matches only), adds 10, 6 or 3 intent points (customer, known organization, unidentified), reports the lead's channel as referral, writes a signal on the referring account and plans a dry-run thank-you task for its owner. The rep's brief, the alert and the CRM task carry an Enterprise line, a Referral line and "Also in from this account" (other people there in the last 30 days). `GET /api/accounts` ranks accounts with enterprise ones first, and the Overview has a Named referrals panel.

Two more things are read by rules and change no score or route. **Feature interest** (`src/interest/`, `docs/DECISIONS.md` #30): each lead is tagged, as it is committed, with the features it showed interest in, by what it wrote (a feature's name or alias), the door it came through (the Signal Ask waitlist, an API key's product), a guide about the feature or the pages an account visited. `GET /api/attribution` serves per feature the counts and a list of who asked, newest first, for customer success to work from at launch. Signal Ask is in the taxonomy as a feature in preview with no launch date. **The team brief** (`src/todayBrief.ts`, #31): `GET /api/brief` answers what the team needs this morning from the read models that exist, with the ids to open each item, and decides nothing. The day I ran against the platform, hour by hour, with what it did before and what it does now: `docs/day-in-the-life.md` (#32).

## Outbound from the rate file

The take-home's outbound analysis (Part 1) runs here as a module (`src/outbound/`, `GET /api/outbound`). At startup it loads Serif's public rate file (`RATES_CSV`, default `data/rates/mrf_rate_search_export.csv`; `npm run rates:fetch` downloads it) when its hash differs from what is loaded, and derives, in one transaction:

- one rate per group (EIN): the row the file flags as covering the most NPIs, then the payer's largest NPI list, then the most psychiatrists, then the higher rate (`sql/models/v_rate_groups.sql`);
- the two contract forms, found by search rather than hard-coded: a rate card (a whole percent of one base, to the cent) and a conversion factor (a whole-dollar multiple of one unit), with how many distinct rates each explains;
- one finding per group: its rate, percent of Medicare, form, the top rate in its city and its size band's median;
- a link to a registry organization by name and state, through the router's own matcher, stored unlinked with its candidates on a tie or a weak match;
- its fit, from the take-home's judgement: behavioral health platforms are the target, small independent groups and hospital systems are not. Platforms come from a hand-made mapping (`fixtures/outbound-platforms.json`); a draft is ready only when the mapping is confirmed and is blocked otherwise.

A team works it through two plays and one status per group (`docs/DECISIONS.md` #27 to #29), read on request so they follow a person's decision, a CRM owner or a new lead:

- **Platform** (the fit above, unchanged) and **System gap** for the Health Systems team: a group that belongs to a registry hospital or health system, has more than 50 clinicians, and is paid at least 20% less than another group in its city (`SYSTEM_GAP` in `src/outbound/plays.ts`). Its draft names the system and the group, the group's rate and the city's top rate, never the group paid it, with every figure inserted by code. Each group shows its play, or why it is in none.
- **Link review**: the loader's link stays the rule (exact), and the near misses are probable (the best candidate in the group's state, when its distinctive name is in the group's name or it scores 0.5 or more). A probable link names no organization anywhere until a person confirms it with `POST /api/outbound/<ein>/link` (served only with `DEMO_ROUTES=1`, because sign-in is not built; the request names who decided). Decisions are stored by EIN in `rate_link_decisions` and survive a reload of the file.
- **Suppression**: a group whose account is in the CRM mirror, claimed by a rep, or had a person come in within 90 days is not prospected. Its status says who has it, it gets no draft, and its finding stays visible as a talking point for them. The platform play obeys it too.
- **Export**: `GET /api/outbound/export.csv`, one row per ready draft with its figures, subject, body and LinkedIn line (`{first_name}` open), quoted for a sequencer or a HubSpot import; `GET /api/outbound/export` counts what is ready, blocked and why, suppressed and by whom, waiting for a link decision, and not a target.

On the August 2026 UnitedHealthcare file (205 rows, 127 groups) it reproduces the take-home's numbers: a $141.47 card that 15 of the 89 distinct rates sit on, a $3.47 unit that 16 are multiples of, and the band counts and medians (`test/outbound-parity.test.ts`, which runs when the file is present). Loading it takes about half a second on the real registry, and a restart with the same file about a millisecond. On the real registry it yields 3 drafts ready (the platform play's 2, and 1 system gap from an exact link: SSM Health in Oklahoma City at 98% of Medicare, against a $306.96 top rate there), 1 blocked, 28 probable links waiting for a person (4 of them would put a group in the system-gap play), none suppressed in a fresh database, and 3 export rows.

`GET /api/outbound/<ein>` renders the take-home's email and LinkedIn follow-up for a platform target, the system-gap draft for a group in that play, or a labelled preview for any other group. Code inserts every figure and returns each one with the field it came from; `{first_name}` stays open, because the file names organizations, not people. Each platform EIN gets one of the two hooks the take-home tests against each other. The HubSpot company upsert carrying the finding, its play and its link status is built for groups in a play that nobody already has, and never sent. When an inbound lead's organization has a rate group, its brief, Slack alert and CRM task carry one line with that group's rate (`leads.rate_fact_json`); scoring and routing do not read it.

The cockpit's **Outbound** tab (after Needs a person) draws it. At the top, the finding in one line and four figures from the API: groups, groups on the card, groups on a factor, and the median percent of Medicare by size band. Then the work: drafts ready per play, groups suppressed, links waiting for a person, and a link that downloads the export. The table of groups comes next, so it is on the first screen (filter chips In a play, Platform, System gap, All, On the card, On a factor and, beside them, status chips Ready, Blocked, Suppressed, Link to confirm and Not a target, each with its count over the other chips; a state and a search; click a header to sort; the group names are buttons, reachable by keyboard) whose Status column reads ready or blocked with the play, suppressed with who has it, link to confirm, or not a target, and, beside it, the selected group's panel: who has it when someone does, the finding as facts, its source rate rows, its registry link (exact, probable, confirmed or rejected, with who decided), its play or why it is in none, the email and LinkedIn line with every inserted figure marked and a table of where each came from, the draft state (ready, blocked with the reason, or preview), and the HubSpot request, collapsed. A plain line says nothing is sent. Under the table, a **Links to confirm** panel lists the probable links in the order of what confirming would do (first the links that would put the group in a play, then those where the organization's name is in the group's name, then score-only candidates), each tagged with what confirming does, with the first one showing and a Show all control; a person types their name once (it is stored as who decided and remembered, and a missing name takes the cursor to the box), and the panel says plainly when the server has demo actions off. Confirm and Reject leave the page where it is: the row becomes one line saying what happened, with an Undo that takes the decision back through `DELETE /api/outbound/<ein>/link`, and a collapsed Decided list holds earlier decisions with their own Undo. Last, the chart of every group's rate against its clinician count (log scale), marked by contract form, with the card's tiers and Medicare's 100% line drawn and the groups in a play named on it. A group's panel has a Copy link. With no rate file the tab says so and shows `npm run rates:fetch`. On a phone-width screen the panel opens as a sheet.

The loop is visible in two places. A lead's trail has a Their rates step when its organization is in the rate file, with the line and a link to the group. The Send a test lead drawer has a preset, Organization in the rate file: an invented person at INTEGRIS Health, which is in the August 2026 file and resolves in the registry, so sending it shows the line in the brief (it does nothing useful with the invented test file, which has other organizations).

## Product usage to pipeline

PostHog knows what accounts do in the product and HubSpot knows which deals sales is working, and nothing joins them, so "I worked on this feature for three months, how did it help sales sell?" has no answer. The usage module (`src/usage/`) joins them on the router's account key.

- `POST /api/usage` takes a PostHog-style batch (`event`, `distinct_id`, `timestamp`, `uuid`, and a company group in `properties`). It is idempotent on the uuid and resolves the company group to an account key; an event the taxonomy (`src/usage/taxonomy.ts`, the one event-name-to-feature table) does not know is stored as unmapped and counted, never dropped.
- Deals (id, account, stage, amount, created, closed, won or lost, add-on if any) stand in for HubSpot's and load from `fixtures/usage/deals.json`.
- **The model is influence, stated simply** (`sql/models/v_usage_deal_influence.sql`): a feature influenced a deal if the account used it in the 90 days before the deal was created or while it was open. Per feature, `GET /api/attribution` gives the accounts using it, the opportunities and closed-won deals it was around (count and amount), the win rate with and without use, the median days from first use to the deal opening, and adoption since launch, each with the counts it rests on. It is influence, not proof of cause, and the API and the tab say so (`docs/DECISIONS.md` #22 says why not weighted multi-touch).
- **Expansion signals** for customer success: a customer account that used an add-on's preview at least 3 times in 30 days with no deal for that add-on, listed with its evidence and a dry-run HubSpot task for the owner. One rule, no routing change.
- `npm run reverse-etl` writes each company's features used in the last 30 days, its last feature use and its per-feature event counts.

- **Interest from inbound** (`docs/DECISIONS.md` #30) is the other half of the join: how many people in the router's own lead stream asked for a feature, by name, by its door, by a guide or by pages an account visited. Per feature, `GET /api/attribution` has an `interest` object (people, accounts, sales-ready, tiers, cues, people since launch) and an `asked` list (account and key, owner, whether it is a customer, the person's name and title, door, cue, a quote of up to 220 characters, when). Signal Ask is a feature in preview with no launch date, so nothing is measured since a launch for it. Interest is not usage and is in no win rate.

The cockpit's **Feature to pipeline** tab (after Outbound) shows the finding and a one-line caveat (influence, not cause) first, then four figures, a chart of the pipeline each feature was around (won, open, lost), a table of the features with their counts beside every rate (a comparison with fewer than 5 closed deals on a side is flagged) and an Interest column, every column of it sortable, the deals behind the selected feature, **Who asked for it** (a compact table: account, whether it is a customer, owner, person, how they showed it, when, and a link that opens the lead in the Lead stream; the quote opens on the row; filters for customers only, sales-ready only and one cue, and a sort by when or by account), and the expansion signals.

The usage data is invented and modest: twelve fictional organizations on `.example` domains (the three in the CRM mirror and nine added there), 22 deals (11 won, 6 lost, 5 open) and 427 events, of which 84 are unmapped and 4 have no account. Signal search is used by nearly everyone, so there is almost nothing to compare it to; most win-rate comparisons rest on fewer than 5 closed deals on one side; one account previewed the add-on and lost the deal; two customers meet the expansion rule.

## Today

The cockpit's **Today** tab (second, after Overview) is where the team starts the morning. It draws `GET /api/brief` in its eight sections (needs a person now, enterprise, referrals, list uploads, expansion signals, outbound, feature interest this week, health), each with a one-line answer, its figures and its first ten rows, and every row is a link to the tab that holds its detail (a lead in the stream, a review item, a rate group, an uploaded list's rows in the stream, a feature). A sticky index at the top jumps to each section with its count; a section shows its top three rows and opens in place to the ten the brief sends, and its "and N more" opens the tab that holds the rest with the matching filter. Under them is an Accounts table from `GET /api/accounts` (all of them, up to 500), enterprise accounts first: name, fact line, owner, score, people in over 30 days, latest activity and signals, with a search, filters for Enterprise only, No owner and Has a referral (each with its count), sortable columns and Show more until every row has shown; an account's name opens that account's people in the Lead stream. It reflows to a phone with no sideways scroll. The brief decides nothing (#31), and nothing on the page sends anything. `npm run brief` prints the same answer as text.

## Using the cockpit: lists, filters and addresses

People who use this scan, narrow, open one thing, act and go back to where they were, so every list is something to narrow, order, link to and act on without losing your place (`docs/DECISIONS.md` #35 and #36).

- **Lead stream.** The route chips (each with its count) and, beside them, Enterprise and Referral toggles, a Tier A to D group, a Team, a Door and a List filter, each showing how many leads it would leave; one Clear filters control and a count line ("12 of 205 leads"). Each row shows what a person filters on without opening it: the tier and score, and small marks for an enterprise account, a named referral (the referrer on hover), an uploaded list and a deal-size cue. The column headers sort (Received, Tier, Score, Organization, Alert; `aria-sort` and an arrow say which). Each uploaded list is one group row at the place of its newest row ("HLTH, 150 rows: 54 B, 79 C, 17 D") that opens in place, and choosing the list in the List filter shows its rows alone. The search also reads list names, rule ids, use cases, referrer names, deal cues and flags. An empty result says what is narrowing it and clears with one click. A lead's trail has a Copy link. On a phone the filters wrap and a lead opens as a sheet over the list.
- **The address.** The tab, the lead or group or feature that is open, the filters, the sort and the search are in `location.hash`, so a view can be linked, survives a reload and comes back with the back button: `#stream?lead=<id>&enterprise=1&sort=score`, `#outbound?ein=<ein>&status=link`, `#feature?f=network_benchmarking`, `#today`, `#review`. Opening an address lands there. Every "Open in ..." control is a link with such an address, and the format is in `docs/DATA-CONTRACT.md` section 13.
- **Overview.** A sticky index jumps to Pipeline, Uploaded lists, Named referrals, Speed to lead, HubSpot and data quality and Live, each with a count. An uploaded list's row and a referrer's row open the Lead stream filtered to that list or that referrer.
- **Times.** Every time is Eastern time with the exact UTC time on hover.

## Tests and CI

Every push and pull request runs `.github/workflows/ci.yml`, and `npm run ci` runs the same sequence locally. It stops at the first failure.

1. `npm run typecheck`: `tsc --noEmit` over the app, scripts, tests and the browser tests, and over the Lead stream, Today, Outbound, Feature to pipeline, Needs a person and How it works tabs' JavaScript files and the address and time modules they share (checked from their JSDoc types).
2. `npm test`: the unit and pipeline tests (976, about seven seconds, no network), among them `test/day.test.ts`, which runs the working day on the test registry. Two of them, the parity check with the take-home, run only when the real rate file is in `data/rates/`; without it they are skipped.
3. `npm run replay:ci`: all 40 fixtures through the real inbound handler, rules only, offline, HubSpot dry-run, commits in strict acceptance order (`COMMIT_GRACE_MS=never`), in its own database and folder (`out/ci/`). It fails the build if the p90 time to route is over `TTR_P90_BUDGET_MS`, set in that script: 150 ms. On Nov 8 the p90 measured 17 ms on this Mac and 35 ms on the GitHub runner, so the budget is about four times the runner's figure: it fails when someone makes the pipeline slow, not when a runner is noisy. With `CI` set, the replay also refuses to start if HubSpot is live.
4. `npm run eval:gate:rules`: the v4 classifier with no model, scored on the sealed and held-out sets. The rules path is deterministic, so its floors (`RULES_FLOORS` in `scripts/lib/eval-gate.ts`) are the measured results with no slack: any drop is a real change in the rules or the date parser. Its output goes to `eval-rules.*` files, never over the model run's `out/eval.json`.
5. `npm run test:e2e`: twenty-six Playwright tests. It starts the server on port 3497 with a throwaway database, the mini registry the unit tests use and the invented rate file, opens the cockpit and (1) sends a test lead through the form, opens it in the stream and checks the decision trail: the resolved organization, a routing decision, and a dry-run CRM sync; (2) sends a lead from an organization in the rate file and checks that its trail shows the rate line the router added and links to the group; (3) opens the Outbound tab, checks the finding, the chart, the default In a play filter, a group's marked draft, the collapsed HubSpot request, the filters and a sort; (4) confirms a probable link in Links to confirm (after checking that a decision needs a name), then checks that the group's system-gap draft is ready and the export has it, and that a suppressed group says who has it; (5) opens the Outbound tab at 390 px with no sideways scroll; (6) loads the tab with no rate file and checks the message and the fetch command; (7) opens the Feature to pipeline tab and checks the one-line caveat, the counts beside a win rate, Signal Ask in preview with its interest column, a feature's deals and the two expansion signals; (8) opens the same tab at 390 px; (9) sends a lead whose message names a customer that recommended Serif, checks the Referral field in its alert preview, and checks that the Overview's Named referrals panel ranks that customer with its owner; (10) sends an enterprise lead that names Network benchmarking, opens Today (the second tab), checks its eight sections and the accounts table with enterprise first, and follows a row into the Lead stream and another into Who asked for Network benchmarking; (11) opens Today at 390 px with no sideways scroll; (12) sends a lead whose company ties between two health systems, and in Needs a person checks that a decision needs a name, chooses one candidate, sees the item replaced by one line saying where the lead went and the tab's count drop by one with the page in place, finds the decision under Decided and as a step in the trail, and finds the name remembered there and in Outbound; Each checks for console errors and failed requests.

`APP_DB`, `OUT_DIR` and `OFFLINE=1` (lookups off) exist so these runs can be pointed away from `data/app.sqlite` and `out/`, which hold the demo. `REGISTRY_DB` and `CACHE_DIR` do the same for the registry: the browser test points them into its throwaway folder, so it runs on the mini registry (decision 28 says why). `RATES_CSV` and `OUTBOUND_PLATFORMS` point the CI replay, the rules-only gate, the browser test and the test helpers at the invented rate file and its mapping in `test/fixtures/`, so no gate depends on the real file being present.

The record of its last run (Nov 9, after the classifier changed) is in `docs/eval-record-2026-11-09.md`, with the hashes in `docs/eval-manifest-2026-11-09.json`. ## Known limits

- The pipeline runs in one process and commits one lead at a time. Each lead's lookups (normalize, resolve) start when it is accepted, four at a time; its rules and any gated model call follow outside that bound. Leads commit in acceptance order within a lane (the email's domain, the address on free mail, the company domain for web intent), and a lead still waiting for its prepared result holds only its lane: after a 250 ms grace (`COMMIT_GRACE_MS`; `never` restores strict order) a ready lead in another lane passes it. So in a burst every lead but the one waiting for the model is alerted in about 250 ms (the 40-event burst: p90 253 ms, against 4.3 s before; `docs/load-record-2026-11-09.md`). A lead that waits for the model still waits for its own call, and with one model slot two such leads wait for each other. Across lanes, round-robin order can differ from acceptance order around a waiting lead, and two lanes that resolve to one account commit in ready order (`docs/DECISIONS.md` #23). `time_to_route_ms` runs from the 202 to the routing decision; the wait for other leads is `timings.queued`.
- An uploaded list (the `event_scan` door, `LIST_DOORS`) is routed on the rules, with the model's call after the alert whatever the note says (`LIST_DOOR_MODEL=gated` restores the gate). Its team-queue, owner-task, nurture and review rows keep their routes, SLAs, review items and CRM tasks but post no alert each: one digest per list and team goes out when the list has settled (`LIST_QUIET_MS`, 5 s after its last scan), so those rows are alerted a few seconds after routing. A rep alert is never folded. A 150-scan list routes in about a second with 6 Slack messages, against 146 s and 74 messages before (`docs/load-record-2026-11-09.md`). Its second opinions still take minutes, one model call at a time, in the lulls. A repeat scan attaches to the scan accepted first whatever order their times are in; a first scan that went to nurture still owns nothing (decision 6).
- The classifier is rules first, with the demo's 3B local model filling gaps on use case and buying role only. Only a lead whose use case the rules cannot settle waits for the model before routing; every other free-text lead is alerted on the rules and gets the same call afterwards, so a disqualifier only the model sees (a vendor pitch, say) reaches RevOps as a doubt a few seconds after the rep was alerted, not before (`docs/DECISIONS.md` #19; `MODEL_BEFORE_ROUTE=all` restores the old order). Second opinions run one at a time and only while no lead is waiting, so a steady stream with no lull delays them, and one that has started holds a lead that needs the model for up to one call. The model never decides urgency: urgency comes from a temporal-expression parser (`src/qualify/when.ts`) that resolves phrases to dates relative to the lead's received time, and a message with no timing language is `unknown`. The model cannot set urgency, override a rule, write alert text or get a lead dropped on its word alone, but its use-case label can change the team for API-type leads (`teamFor` in `src/route.ts`). Combine policy is v4; v1 to v3 stay callable. `npm run eval` scores rules, model, v1, v2, v3 and v4 on the dev fixtures, the held-out set and, if `fixtures/heldout-sealed.json` exists, a sealed set, and writes `out/eval.md`.
- A door that is meant to be signed fails closed. Calendly is the only one: with `CALENDLY_SIGNING_KEY` missing or blank, `POST /api/inbound?source=calendly_demo` answers 503 naming the setting and records nothing, and the server logs one warning line at start. `.env.example` is documentation only and is never loaded, so a missing key stays missing. `npm run dev` and `npm run replay` set a local demo key inline (`local-demo-signing-key-not-a-secret`, not a secret), which is what lets the cockpit's send-a-lead form and Replay a day (which sign server-side) work. The other doors are unsigned by design.
- Local only by default: the server binds to 127.0.0.1 (`HOST` overrides), and the cockpit's write routes (those under `/api/demo/`, `POST /api/outbound/<ein>/link`, `POST /api/leads/<id>/review` and `POST /api/review/list`) answer 404 unless `DEMO_ROUTES=1` (`npm run dev` sets it). The read endpoints (`/api/leads`, `/api/metrics`, `/api/dashboard`, `/api/stream`) have no authentication, so do not expose this server to a network.
- The homepage-title lookup fetches a domain taken from a stranger's email address, so it takes a plain DNS hostname only, refuses any name that resolves to a private, loopback, link-local, CGNAT or unique-local address, and follows at most 3 redirects, https only. It checks the name before the fetch and `fetch` resolves it again, so a DNS answer that changes in between is not caught; closing that needs the connection pinned to the checked address.
- The rep alert goes out before the HubSpot write. A live HubSpot plan goes to an outbox in the database and is delivered outside the one-at-a-time section, oldest first; a network error, a 429 or a 5xx is retried with backoff (honoring Retry-After) for about four minutes, then marked dead and shown on the dashboard. Delivery is strictly in order, so one plan waiting for its retry holds the plans behind it. A link from the alert to the HubSpot record would have to be a follow-up message, because the record may not exist when the alert goes out.
- A lead whose run throws is retried twice (after 5 s and 10 s), then given up: status `failed`, and RevOps gets an alert payload through the same Slack recorder. A re-run, by retry or by boot recovery, can send the rep alert a second time when the earlier run failed after it. Retries run on an in-process timer; a stopped process picks them up at the next boot.
- `npm run eval` also writes `out/eval-manifest.json` and a Provenance section at the top of `out/eval.md`: SHA-256 of the sealed set, of each classifier source file and of the whole classifier, the model and temperature, and the per-set results. `npm run eval:gate` compares the classifier hash with the previous recorded run and fails below the floors (sealed urgency 22/24, use case 17/24, disqualifier 21/24; held-out 21/24, 19/24, 22/24). The hashes make later edits detectable. They do not prove when the sealed set was written; file modification times are recorded as supporting evidence only.
- Treat the eval numbers with care. The dev fixtures were written alongside the rules. The held-out set was used to build the date parser, so it is a development set too (v4 urgency 22/24 there). The sealed set (24 items, written before the date parser was built and kept outside the project until the classifier code was frozen, as its own note records) scores 23/24 on v4 urgency, 18/24 on use case and 21/24 on disqualifier in the Nov 9 run (22/24 on Nov 7, before the classifier changed; see `docs/DECISIONS.md` #9). The classifier code was edited after the sealed set had been scored, so read the sealed numbers as a regression check.
- Because silent messages are `unknown`, their intent score has no urgency points. That is deliberate. Several gold labels on the dev fixtures expect `exploring` or `this_quarter` for such messages, so dev urgency accuracy is lower than the rules-only column.
- Dates resolve against fixed conventions (a bare month is the 1st, "mid" is the 15th, a bare year is July 1, "next quarter" is its first day). Some gold labels disagree with those conventions; they are listed as label questions in the eval and not edited.
- Resolution depends on the registry. A company that is in none of CMS, AHRQ, the curated list or NPPES, and whose domain is not mapped, ends as `unknown_org` and goes to review (or, with a benefits title, to a low-confidence inferred employer). The AHRQ file is the 2023 compendium; systems that merged since may be named by their old record.
- Homepage-title and NPPES lookups use the network on first sight of a domain and are cached under `data/cache/`. With the network off they degrade to unresolved and the reason is recorded.
- HubSpot live mode has run against a developer test portal, not a production one. On Nov 7 it loaded the 40-event day (39 leads). Running the day again counted 126 requests: 101 writes (company and contact upserts and the contact-to-company association) returned 200, and the 25 tasks were already open and were reused, not created. It created no new records. That run confirmed the two endpoint shapes the documentation did not show (see `docs/DATA-CONTRACT.md`). A production portal's existing schema, owners and rate limits are untested.
- The outbound module's card and factor are inferred from the rates. The take-home also checked that neither is luck by nudging the rates at random and searching again; that check is not ported, so the stored hit counts are what a reader judges by (a pattern needs at least 3). One sentence in the drafts (every large group above 115% of Medicare is a hospital system or academic medical center) is a reading of the names in the August 2026 file, kept as a constant; a different file needs that reading done again. By name and state alone, 12 of the 127 groups link to a registry organization ("exact" in link review; one of them, INTEGRIS HEALTH GROVE HOSPITAL, is a strong match at 0.915 rather than an identical name). The rest stay unlinked with their candidates: physician groups and practices the registry does not hold, and hospital-affiliated names that do not reach a unique, strong match (Parkland Health's best candidate scores 0.58, under the router's 0.7 floor). 28 of those are probable and wait for a person; some of their candidates are wrong (UT Physicians' is a hospital called Physicians Centre), which is why nothing is linked until someone confirms. Sign-in is not built, so a link decision records the name the person typed, and the route is served only with the demo actions on. Suppression reads the CRM mirror, the router's claims and its leads, not HubSpot itself, and an inbound lead stops suppressing 90 days after it came in.
- The cockpit is a desktop console, built for 1240 px and up. The shell above the tabs, the Lead stream (a lead opens as a sheet over the list), the Today tab, Needs a person, the Outbound tab and the Feature to pipeline tab reflow to a phone; the other tabs keep their desktop layout and scroll sideways inside their own area. The Outbound chart is drawn at the width its box has, so it is readable at 390 px, and its marks can be clicked but not tabbed to: the table is the keyboard route to every group.
- The attribution model is influence over time windows, not a causal estimate. A deal counts fully under every feature its account used around it, so features overlap; accounts that use more features are probably bigger or more engaged to begin with, which the comparison does not remove; and at 22 deals most rates rest on a handful. Windows are measured to the newest event, not the clock. Events and deals are synthetic, and the real joins are not built: PostHog would post to the same endpoint from a webhook destination or an export, and deals would be read from HubSpot's deals API. A redelivered event keeps its first copy, and an event stored before its account existed stays unresolved. `POST /api/usage` is unsigned, like the doors other than Calendly.
- Round-robin capacity is 6 alerts per rep per rolling 24 hours, a placeholder.
- A decision records the name the person typed, because sign-in is not built. A link decision in Outbound can be taken back (Undo); a review decision cannot be undone in the product: a second decision on an item is refused, and a lead still running cannot be decided. Running the lead again can repeat an alert, as any re-run can. Ruling a lead not a buyer after its rep was alerted releases the rep's claim and sends the rep no message of its own; the doubt's follow-up already said RevOps was checking. The decision's `person` method is added outside the frozen classifier types (`src/review/resolution.ts`).
- The enterprise definition is a starting assumption (`ENTERPRISE_DEFINITION` in `src/enterprise.ts`) and rests on the registry's firmographics, so a system the AHRQ file sizes wrongly is routed by that size. Deal-size cues are the prospect's own words, so a prospect at a known organization can write "budget is approved" and reach a named rep sooner; that is the intent of the rule, and it never changes the tier. On the base fixtures it moves five tier-B leads from a team queue to a named rep (`docs/DECISIONS.md` #25).
- Referral capture is phrase-based. A referral worded another way ("Jane at Emory said we should call you") is missed, and a short or common name ("Emory") resolves only when the registry's matcher finds a unique, strong match. The thank-you task is planned on the lead and never sent.
- Feature interest is rules over words, doors, guides and visited pages (#30). A message that asks for a feature without naming it is missed, the aliases are a hand-made list, and a customer who uses a feature but never wrote or visited is in the usage numbers and not in the interest ones. The counts are people in the lead stream, one per contact, and leave out leads routed as not a buyer.
- The brief reads the same read models as the dashboard, so its health figures (queue wait, and time to alert for leads with their own alert) cover every lead and not its window, and the review-item waits and the Today tab's accounts are as current as the last read. In `npm run day`, which runs on a fixed clock, every duration reads zero; the timed figures are in `docs/load-record-2026-11-09.md`.
- Scoring weights are hand-set. Closed-won and closed-lost data would be needed to fit them.
- In the test suite and CI, the Slack and HubSpot paths run against stubbed network calls; nothing is sent.
